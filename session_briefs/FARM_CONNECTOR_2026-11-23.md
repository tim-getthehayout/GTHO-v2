## 1. Outcome

Each farm gets its own Grok Bot that uses GTHO through one **farm-scoped GTHO connector** (a remote MCP server). In the test phase the connector is wide (reads and writes every table on that farm, events included, under RLS as the farm's bot login), and every save is previewed to the farmer and committed only after their yes (Ts=B, Wr=C), so real use shows what the final connector must be. Every call is **captured**, and Design turns the capture into the narrowed connector spec (P3). A **shared onboarding bot** reads a new farm's documents and saves its base data straight into GTHO; every onboarding write is tagged to the session and source document, reviewed afterwards by Tim and Design, and can be corrected or undone per session.

**Client-neutral (Tim t1416u, 2:25 PM ET; card t1417s5582, 2:31 PM ET — docs note, not a new lock).**
1. **`gtho-mcp` holds no Grok Bot-specific logic.** Farm scope (one-farm pin, RLS as the bot login), the preview/confirm token, archive-only, the stale-write check, the per-call membership recheck and capture are all enforced server-side, so any MCP client using the standard OAuth sign-in works the same way.
2. **Template instructions and skills under `bots/templates/` are plain, portable text.** Safety never relies on a Grok Bot-only feature, so the same text doubles as a hosted assistant's system prompt.
3. **Capture records which client made each call:** a `client` column on `connector_calls` (and `onboarding_sessions`), values such as `grok_bot`, `gtho_hosted`, `other`, derived from the OAuth client id. It is part of the already-planned P1 migration — no extra migration.
4. **A future GTHO-hosted assistant** that calls the xAI Grok API from our backend uses the same `gtho-mcp` tools / OI-0215 actions **as a farm bot login** (same provisioning) and **never the service role**. This converges OI-0210/0215 (today's `gtho-assistant` reads farm data with the service role) onto one safe path. That is a later OI, not P1 scope.

## 4. 0282-C — farm-scoped GTHO connector

### 4.1 Hosting (Design default; not a Tim question)
**H1 (default): Supabase Edge Function `gtho-mcp`** (Streamable HTTP MCP) in the same project and deploy path as the assistant functions. Public HTTPS that Grok Bot can reach, next to the database, imports `src/entities` and `src/calcs` like the assistant already does. Alternative H2 — a small Node service on the VPS behind Caddy — adds new public surface and DNS/Caddy work owned by Homelab Build; homelab apps stay home-only. Revisit only if Edge limits (time, memory) block bulk onboarding.

### 4.2 Auth (Design default under L1)
- **Supabase Auth OAuth 2.1 server** (beta; enabling it is a production Auth setting → Tim's yes) with a small in-app consent page. The farm's Grok Bot connector does a one-time OAuth sign-in **as the farm's bot account**; tokens refresh automatically. Every connector call uses that account's JWT, so **RLS applies as the bot account**. The connector never uses the service role for farm data.
- **Farm pin:** the connector resolves the account's accepted memberships on every call and serves exactly one operation; 0 or more than 1 → refuse (`one-farm-per-account`). Bot logins are `operation_members` rows with role **`bot`** (Sg=A′; cannot manage members, cannot change their own role after OI-0233). Adding `bot` to the role list (entity `VALID_ROLES` and any DB check) is part of the P1 migration → Tim's yes + backup at apply.
- **Credentials outside chat:** bot logins are created inside the connector's connect step (Sg=A′, §4.6); no password or token is ever shown to the owner, the bot or the chat; sign-in secrets for the bot login are generated and held by GTHO/Supabase only, never in chat, docs or logs. Revocation = Disconnect in the Connected assistants list (membership removed + sessions/refresh tokens revoked); the next call fails closed.
- **Fallback if Grok Bot's connector OAuth cannot complete against Supabase's OAuth server:** a GTHO-issued per-connection token (stored hashed) that maps to the bot account's own refresh session. This keeps RLS-as-user but stores a session credential at rest; it needs a Design security review before use. Decide after a P1 spike.

### 4.3 Tool surface — LOCKED Ts=B (card t1400s5504)
- **Table-level read/write on every farm table, events included,** under RLS as the farm's bot login, through generic tools: `list_tables` / `describe(table)` (columns from the entity `FIELDS`, plain meanings, units), `list` / `get` (filters, paging ≤ 500 rows), `insert`, `update`, `archive` per table. Where an entity module exists (`src/entities/*.js`), every insert/update runs its `create()` defaults → `validate()` → `toSupabaseShape()`; tables without one get column type/required checks from the schema. The server sets `id`, `operation_id` and `farm_id`; the model never supplies them. Events, paddock/group windows, feed entries, feed checks + items and batch moves/adjustments are **writable**. The earlier “events read-only” limit is removed.
- **Named calculated reads** reuse `src/calcs` only (existing three + `event_feed_outlook`, `paddock_readiness`, `feed_inventory`, later `dmi_target_vs_actual` from OI-0280). The model never computes farm numbers itself.
- **Guarded read-only SQL over approved views: deferred.** OI-0215 §7's view-security proof (views bypass RLS by default) comes first; the generic list/get tools give breadth meanwhile.
- **Risk — half-finished workflows.** Move/close, feed check with items and delivery span several tables; done row by row they can leave partial states (e.g. a window closed without the new one opened; a check without its items; OI-0226 invariants). **Mitigations:** (1) the bot templates' skills (`bots/templates/`, §4.6) spell out the correct row order and the complete set of rows for each of these workflows, and batch them in one preview/commit where possible; (2) capture flags **partial sequences** (a workflow's opening row with no closing rows within the session or within 10 minutes) in the weekly review; (3) **workflow tools (P1b)** that reuse the app's own save code remain the follow-up the usage logs will justify.

### 4.4 Write safety — LOCKED Wr=C (card t1400s5504) and delete rule Dl=A (Tim 👍 12:52 PM ET)
- **Preview and confirm every save.** Every write tool (`insert`, `update`, `archive`, bulk) first returns a **preview**: the before/after rows as a diff, the validation result, and a **one-time confirm token** bound to that exact payload (hash of operation, actor, tool, table, rows and the `updated_at` values read), expiring after **10 minutes**. Nothing is saved at preview. The bot shows the preview to the farmer in chat; only after the farmer's yes does it call `commit(token)`. Commit rejects an expired, reused or mismatched token (payload tamper), and **re-checks the stale-write guard**: if any row's `updated_at` changed since the preview, it refuses with `conflict` and the bot must preview again. A batch uses **one preview and one confirm**. Capture logs the preview and the commit as two linked rows.
- **Deletes — LOCKED Dl=A (Tim 👍, 12:52 PM ET; changeable later at Tim's call):** archive or soft-delete only, always restorable; **no hard-delete tool**. Tables without an archive/soft-delete column are not deletable through the connector (logged as a gap if asked). Option B (hard deletes with the same preview and confirm) stays available if Tim changes it later.
- Every committed write is logged with its before/after image so it can be undone.

### 4.5 Limits and stamps (Design defaults)
60 calls/min and 5,000/day per connection; bulk ≤ 200 rows per preview/commit; reads ≤ 500 rows per page; 10 s per call. Writes refuse if `operations.schema_version` is above the connector's compiled ceiling (same rule as the PWA). Every response and log row carries connector version, tool version and schema version.

### 5.1 Capture — LOCKED Cp=A and Sf=A (card t1400s5504)

Farm members read their own farm's rows. Tim reads other farms' rows only per **Sf**. Retention: 90 days raw (same as assistant artifacts); onboarding write logs kept until that session's audit is signed off, then 90 days; weekly digests kept. Excluded from CP-55 backups (operational telemetry, not farm data); MIG doc note at build time.

### 5.2 Shared onboarding bot access (Design default under L3)
- **Per-farm onboarding login per session:** for each new farm, a fresh onboarding login (e.g. “GTHO Onboarding — <farm>”) that is a `bot`-role member of **that farm only**. The farm owner creates it the same way as the farm bot's login (the connector's connect step, Sg=A′; fallback screen only if the P1 spike fails), with a session end that switches it off. Because L3 locks a per-session login, onboarding uses one under every Sg option. The shared onboarding bot connects its GTHO connector by signing in as that login at session start (OAuth on the GTHO login page). At session end: membership removed, login disabled and signed out, connector disconnected, session marked ended. Isolation stays in the database: an onboarding login is never in two farms, and the one-farm pin (§4.2) refuses otherwise.
- Rejected: one long-lived onboarding account that joins and leaves farms in turn. A missed removal would leave it in two farms and RLS would then show both.
- The farm owner signs up and runs the existing 4-step wizard first (creates operation, farm, membership, seed classes); the bot does not create operations.

### 5.3 What onboarding needs from the connector (P2)
- Document ingest is done by the bot with Grok Bot's own file tools (PDF, spreadsheets, photos of herd lists, paddock maps, feed inventory). The connector receives structured rows only.
- `bulk_insert` per table (≤ 200 rows) through the same **preview → farmer's yes → commit(token)** flow (§4.4; the preview is the dry-run: validation results per row, nothing saved); natural-key **dedupe** (location/group/class/feed-type name per farm, animal tag per farm, batch label + date) — duplicates are reported, not silently merged; clear per-row validation errors in plain field terms; optional bot-supplied row reference echoed back.
- `onboarding_checklist` read: farm settings + units, locations with area, groups, classes with weights/DMI, animals with class and group, feed types and inventory batches; what's missing.
- `start_onboarding_session` / `end_onboarding_session`; every write in a session carries session + source document.

### 5.4 Post-save audit (L4)
- **Audit report** per session (in-app Settings → Onboarding audit for farm members and Tim; same data in the capture tables): rows created/changed per entity, source document per row, validation warnings, dedupe hits, gaps, and suspicious values (area 0 or > 2,000 ac, weight outside class range, duplicate tags).
- **Correct:** ordinary edits in the app, or via the connector, logged against the session.
- **Undo session:** preview first (lists what would be reverted and any blockers), then commit only with Tim's explicit yes. Under **Dl=A** undo never hard-deletes: rows created in the session are **archived/soft-deleted (restorable)** if nothing outside the session references them (else listed as blockers); created rows in tables with no archive column are listed for Tim to decide; updated rows restored to their before image if unchanged since; archives reversed. Undo writes are logged as `undo`.
- Tim and Design review each session's report and sign it off; findings feed the onboarding bot's instructions. Tim's farm, then the second test farm, before any outside farm.
